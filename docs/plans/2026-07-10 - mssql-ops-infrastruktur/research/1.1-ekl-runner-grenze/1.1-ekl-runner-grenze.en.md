# EKL Migration Runner (excel_ekl) — Boundary Analysis for grate/RoboticoOps

> Source: Opus agent "ekl-runner-boundary", session 2026-07-09, read-only audit of `/home/lukas/WebStorm/excel_ekl`.
> **Central finding: the EKL runner is NOT cleanly confined to `RoboticoEKL`** — it also inhabits `CustomWorkflows` and writes into `dbo.tWorkflow`/`tWorkflowAktion`.

## 1. Runner mechanics

- **TypeScript CLI** (`scripts/jtl-migrate.ts`, Commander; npm `migrate:jtl`), commands `status | up | validate | create | backup`. **No auto-run at app start** — boot only checks (health plugin, policy `jtl: 'error'`: pending migrations = fatal startup error with instructions; auto-apply only with an explicit `'auto-migrate'`).
- Active path: `backend/src/infrastructure/migration/jtl/JtlMigrationOrchestrator.ts` (the older `MssqlMigrationAdapter.ts` is deprecated). Driver `mssql`/tedious; `up.sql` is split on `^GO$` and executed batch by batch — **no overarching transaction**; each file brings its own `BEGIN TRAN`+`IF NOT EXISTS` idempotency.
- **Layout:** `backend/migrations/jtl/NNN_snake_case/` with `up.sql`, `verify.sql`, optionally `pre-check.sql`, optionally `data-migration.ts`; a central `manifest.json`. Integer versions, at 026 in the main tree.
- **Journal `RoboticoEKL.tMigrationHistory`:** `nVersion`, `cFileName`, `cChecksum` (SHA-256), `bSuccess`, `cErrorMessage`, `cAppliedBy`; UNIQUE(nVersion)+UNIQUE(cFileName); writing = MERGE on nVersion (one row per version, last attempt). "Applied" = `bSuccess=1`; FAILED counts as pending → re-run. **`cChecksum` is written but NEVER checked** — an applied up.sql edited after the fact is not detected.
- **Locking:** `sp_getapplock`, resource **`RoboticoEKL_Migration`**, Exclusive, transaction owner, timeout 30 min. Advisory (serialises EKL runs only).
- **Backup:** `up` enforces a full backup of the entire target DB before every migration. No `down.sql` — recovery = restore.

## 2. Scope boundary — reaches beyond RoboticoEKL

CREATE targets: 63× RoboticoEKL, **4× CustomWorkflows**. No dbo table DDL, but:

- **Creates the `CustomWorkflows` schema** (016, 023) and creates `spCMArtikel`, `spCMArtikelNeu` in it — **the same schema JTL-Robotico populates**.
- **Consumes JTL-Robotico's CW registration infrastructure:** `CustomWorkflows._CheckAction`, `._SetActionDisplayName`, `vCustomAction` (guarded, otherwise only a PRINT warning). These belong to JTL-Robotico; EKL expects them to be present.
- **Writes into `dbo.tWorkflow`/`tWorkflowAktion`** (017, 023, 024): creates active JTL workflows; 017 deactivates existing JTL workflows (`UPDATE dbo.tWorkflow SET nTyp=2`). Idempotency via a `cName` marker ("EKL …").
- **Steady-state DML in dbo** (at runtime via SPs): tArtikel, tArtikelLabel, tArtikelShop, tShopUeberverkaeufeMoeglich, ebay_item, ebay_logbuch and others.
- **FK couplings to JTL dbo:** RoboticoEKL tables reference dbo.tArtikel/tLabel/tWarengruppe/tBenutzer (some with ON DELETE CASCADE).
- **No grants/logins/users/server objects** — the runner creates no principals.

## 3. Target DB configuration

- Env-driven (node-config cascade, `--environment=<name>`, TTY confirmation for prod). One run = exactly one DB. Environments: test-docker, test-mssql, test-production/test-staging (**VM-SQL-Test-1**), production (**vm-sql2**, eazybusiness).
- **No reference to `eazybusiness_tm2/3/4`** — the EKL runner never runs against the test-mandant clones, only against the respective main eazybusiness (evidence: prod run 2026-07-02, v1–v24 on vm-sql2).

## 4. Collision surfaces with grate/RoboticoOps

- **HARD collision: `CustomWorkflows`.** Both chains write into the same schema. grate must never touch `spCMArtikel`/`spCMArtikelNeu` or EKL rows in `dbo.tWorkflow` (cName `EKL …`). Conversely: if the registration infrastructure (`_CheckAction` etc.) is renamed/removed, EKL 016/017/023 break.
- **The journal travels with the clone:** EKL copes with that (idempotency + bSuccess skip, no checksum check). **grate checks hashes** → never edit one-time scripts after they have been applied (standard discipline; `--warnononetimescriptchanges` as an emergency valve); an anytime hash mismatch is harmless (re-run).
- **Separate locks/journals:** the grate journal lives in its own schema (Robotico or RoboticoOps), no conflict with the `RoboticoEKL_Migration` applock.
- **RoboticoOps:** invisible to the EKL runner (which knows only its one DB) — zero contact.

## Binding boundary definition

**EKL runner ownership (grate must NEVER touch):**
- Schema `RoboticoEKL.*` in full, including `tMigrationHistory` + the applock `RoboticoEKL_Migration`.
- In CustomWorkflows: `spCMArtikel`, `spCMArtikelNeu`.
- `dbo.tWorkflow`/`tWorkflowAktion` rows with cName `EKL …`.
- EKL-driven state in dbo (tArtikelLabel etc.).

**JTL-Robotico/grate ownership (EKL consumes it and relies on it):**
- The CW registration framework: `_CheckAction`, `_SetActionDisplayName`, `vCustomAction` — **keep names/signatures stable** (an API for EKL!).
- `Robotico.*` (EKL-012 reads `Robotico.fnEscapedCSVParseLine`, for example — that too is a consumed API).
- The new RoboticoOps DB.

**Shared zone (additive only, coordinated):** the `CustomWorkflows` schema as a container is jointly inhabited — each side only its own named objects, no DROP SCHEMA, no deleting foreign objects; idempotent `IF NOT EXISTS` schema creation is compatible on both sides. `dbo` (JTL vendor): both only under the same idempotency/ID-by-name rules.

## Transferable lessons

1. **Own schema + own lock/journal namespace for grate** — the only remaining collision surface is the additively shared CustomWorkflows.
2. **Clone robustness is a design constraint:** the journal travels with every clone; never edit one-time scripts after they have been applied; anytime re-runs must be inconsequential.
3. **GO split without an overarching transaction → enforce object-granular idempotency** (grate: use `--transaction`, still write idempotently).
4. **No hard-coded JTL IDs — always resolve by name**; pre-checks as hard FAIL, not WARN (the sharpest EKL prod risks came from test DB IDs).
5. **Deploy strictly manually, with a backup, never auto-apply** — adopt the EKL positions (CLI + enforced backup + prod confirmation).
